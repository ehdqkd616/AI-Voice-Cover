# UVR-MDX-NET (and other audio-separator-supported architectures) —
# isolated in its own worker image/venv, NOT layered on top of
# requirements.txt like the other worker Dockerfiles do. Two independent
# reasons:
#   1. audio-separator pulls in a much newer torch than the RVC engine is
#      pinned/verified against (torch==2.4.1 in requirements-gpu.txt);
#      mixing them in one environment risks pip silently upgrading torch
#      out from under RVC.
#   2. audio-separator requires numpy>=2, which directly conflicts with
#      requirements.txt's numpy==1.26.4 (pinned there for librosa/scipy
#      compatibility in the OTHER workers) — pip's resolver can't satisfy
#      both in the same environment at all (ResolutionImpossible), not just
#      "risky", so this file intentionally does NOT build on requirements.txt.
# This is a fully self-contained requirements file — every package this
# container needs, not just the MDX-specific ones.
#
# CPU-only (onnxruntime, not onnxruntime-gpu) — deliberately, not just for
# lack of trying. GPU was tested and rejected: onnxruntime-gpu's current
# release targets CUDA 13, which dropped kernel support for this host's
# Pascal-generation GPU (GTX 1050 Ti, SM 6.1); pinning an older CUDA-12
# onnxruntime-gpu build works for provider *activation*, but audio-separator's
# transitive dependency on onnx2torch-py313 forces torch to a version that's
# ALSO past Pascal's support window, so actual inference (torch.stft) fails
# with "no kernel image is available for execution on the device" regardless.
# Fixing this would mean hand-pinning several transitive deps below what
# audio-separator's own dependency floor wants — fragile, likely to break on
# any audio-separator update. Not worth it for a personal deployment where
# CPU (~20s-2min per song, measured) is already fine.
